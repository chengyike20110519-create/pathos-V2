# Supabase 后端数据审计

检查日期：2026-10-19，约 19:56（中国标准时间）。

## 结论

**容量暂时充足，当前数据能被网站读取，但还没有达到可以放心、大规模持续导入并对外开放的状态。优先风险是访问权限、来源追溯和审核链路，不是数据库装不下。**

之前的“94/94 接口通过”只证明当时可以读取并通过前端格式解析，不能代表 94 校资料全部经过复核，也不能代替安全、备份和扩容检查。

本轮只做当前实库快照、数据一致性检查、少量连通性抽测、查询执行计划检查和扩校元数据的内存回放。没有修改数据库、权限或应用业务代码，没有执行迁移、导入、删除、清理，也没有读取用户个人记录的内容。学校数据查询置于强制只读事务中。

## 2. 最高优先级：访问权限

34 张 public 业务表中，6 张开启了行级保护，**28 张没有开启，且 anon 角色拥有 SELECT、INSERT、UPDATE、DELETE 权限**。

涉及学校研究、学校指南、政策事实，以及未来可能存放账号、会话、选校清单、报告、联系方式的业务表。后者本次计数均为 0，未读取任何个人记录内容；表为空不代表权限配置可以忽略。

本轮在只读事务中临时切换为数据库 `anon` 角色，只查询学校记录数量，复现如下：

| 数据表 | 匿名角色可见记录数 |
| --- | ---: |
| universities（已开启行级保护） | 0 |
| school_research_records | 94 |
| college_guides | 88 |
| school_confirmed_facts | 97 |

这是数据库角色层面的有效权限验证；**没有进行匿名写入测试，没有证明已经发生外部泄露或篡改**。本地没有可用的匿名/公开 API key，因此没有进一步验证 Supabase Data API 的实际开放配置。如果这些表处于 Data API 开放范围，匿名访问就可能绕过网站自身的登录检查。[Supabase 官方安全说明](https://supabase.com/docs/guides/database/secure-data)

数据库迁移记录停留在 013；本地 014 的权限保护迁移未出现在已执行记录中。仅应用 014 也不足以覆盖全部 28 张业务表，仍须逐表设计权限。网站当前采用 BFF 连接数据库的方式，应评估收回匿名角色权限、关闭不需要的 Data API 暴露范围，并为服务器使用最小必要权限。

**建议：在扩充数据或开放真实用户注册前先处理。此次检查没有自动修复权限。**

## 3. 数据质量及来源缺口

### 3.1 通过的完整性检查

- 94 所学校都有详情和研究记录。
- 没有检出学校—详情 ID 不一致、孤儿详情、孤儿研究记录、孤儿政策事实。
- 没有检出重复的归一化校名、重复 UNITID、重复学校—事实类型键或非法坐标。
- 研究快照中已有数值的录取率、毕业率、保留率、人数、学费和 SAT 区间未检出本轮定义的基础范围错误。
- 7 条特色/优势记录通过当前字段门禁，并均能匹配本校目录名称。

以上不能证明历史上从未丢失或篡改过数据：当前没有可用的完整历史版本链用于逐次回放。

### 3.2 专业“有名称”不等于“资料齐全”

- 4,130 条目录记录目前只是名称字符串，没有逐条保存来源编号。
- 80 所学校的详情中，至少有一个来源编号无法在当前 source_index 中找到；按学校累计有 306 个这样的引用，可能重复引用同一个编号，不能当作 306 个不同来源。
- 当前来源索引有 307 条、编号不重复；1 条没有可用的 HTTP(S) 链接。没有链接可能是明确的来源受限占位，不一定是错误网址。
- 6,877 条目录记录均没有单独的 listType/kind 字段；部分名称已带学位后缀，但尚不能统一按主修、辅修、学位项目、方向进行结构化筛选。
- 只有 2 校拥有已接通卡片的本科优势专业证据；其余学校不能自动从“开设”或学校综合排名推断“专业强”。

这些问题主要影响证据展示、专业分类和学校间比较，不足以直接推断所有对应名称都是错误的。来源断链和无逐条来源的两组记录也不能直接相加。

### 3.3 政策数据存在“两套链路未接通”

- 旧的 school_confirmed_facts 存有 94 条标化政策文字备注，状态标为 confirmed。
- 同时，94 份学校详情里的 testPolicy 和 englishPolicy 字段都仍是 pending_external_access。
- 新的 facts/sources/source_documents/review_tasks 审核链目前均没有数据；Stanford 的已审核事实接口返回 0 条。

因此，不能说这些学校“完全没有政策资料”，也不能说已有备注已自动成为前端可比较、可追溯版本和有效期的结构化政策。备注需重新核对适用年份、申请人范围及有效性，再纳入同一审核/展示链路，而不是根据文本猜测政策。

### 3.4 原始字段、年份与费用口径仍需治理

- 32 校仍有原始元数据结构缺口，例如录取率字段为空对象。前一轮前端解析修复可以防止崩溃，但并没有把这些数据库字段补成真实数据。
- 62 校仍存在有值且参考年份早于 2024 的元数据，主要为 2019 年在校生字段；另一些学校仅残留旧年份的空占位，不能把空占位也说成旧事实。
- 较新的研究快照可用于补充部分缺失数值，但展示时必须同步它自己的统计年份、来源和状态，不能沿用旧字段标签。
- 原始费用共有 122 条，部分仍为 2023–24 学年；67 校存在不能直接映射为国际生/本州/外州口径的费用记录，包含私立学校单一费率等情形，不代表费用数值一定错误。
- 现有转换代码使用固定 7.2 将美元换成人民币，部分派生结果被标为精确验证。这只能作为估算换算，不能当作实时人民币学费，需明确汇率、日期、对象及包含项目。

当前研究快照可用数值覆盖如下；这是“字段有数值”，不是本轮重新向官网核验后的准确率：

| 字段 | 覆盖学校 |
| --- | ---: |
| 本科人数 | 94/94 |
| 录取率 | 92/94 |
| 毕业率、保留率 | 各 92/94 |
| 本州、外州学费 | 各 93/94 |
| SAT 阅读及数学 25/75 分位 | 各 79/94 |

录取率、毕业率、保留率缺数的研究快照为俄亥俄州立大学、南卡罗来纳大学哥伦比亚分校；后者学费也缺数。SAT 缺失包括部分采用不同考试政策的学校，不能强行补值，也不能仅由分数缺失反推出政策。

## 4. 扩校回放：不是容量限制，而是预览契约锁定

本轮读取当前实库 manifest，在内存中复制并修改计数，没有往数据库插入学校：

| 回放场景 | 当前程序结果 |
| --- | --- |
| 当前 94 校元数据 | 通过 |
| 学校/摘要/详情数一起改成 95 | 拒绝：manifest counts must be 94/94/94 |
| 已验证记录数从 904 加 1 | 拒绝：manifest verifiedRecordCount must be 904 |

说明当前解析仍锁在一个固定的 94 校预览集。它不代表 PostgreSQL 最多能存 94 所学校，也不意味着第 95 所学校的所有接口必然崩溃；但更新元数据后，该元数据接口会因校验失败而不能正常发布。只插数据、不改计数，又会留下不一致的元数据。

必须先把固定数量校验换成动态一致性校验：按同一批次核对实际学校、摘要、详情数量、唯一 ID、有效来源和数据版本。

地图单次最多 250 校的展示保护和专业目录索引最多 5,000 校的边界也需要保留明确提示、设计分页与按条件查询；后者不应在扩量后继续把全库专业名单搬到前端。

此外，当前 health/ready 只把 001 视作必需迁移，因此虽返回 ready，也不能证明 014 权限迁移已执行。这类健康检查不能充当安全验收。

## 5. 速度与稳定性

- 本轮全校详情接口回归：94/94 成功，0 个格式/请求失败；中位数 385 ms，P95 3,406 ms，即约最慢 5% 的请求已到 3.4 秒或以上。
- 最后一组独立数据库新连接：5/5 成功，连接建立约 527–653 ms；同连接 SELECT 1 网络往返约 83–121 ms。
- 三个代表性数据库查询样本的服务端执行时间约为：按州取点位 0.068 ms、专业目录匹配 14.081 ms、详情来源关联 1.101 ms。样本不是全站所有 SQL，也不包含网络、BFF 全部处理和浏览器渲染。
- 最后一组个别 API 抽测命中进程缓存，约 4–5 ms，不能据此声称冷启动秒开。
- 前一轮已记录过数据库 ETIMEDOUT、点位约 12 秒和详情重试约 27 秒的慢样本；本轮短时成功并不能证明间歇性问题已根治。

现有证据不支持“39.6 MB 的数据库太大，所以地图慢”这个结论。后续应分开记录连接耗时、服务端 SQL 时间、响应体积、BFF 处理和首屏时间，并检查长尾连接问题。此次没有进行大并发/长期稳定性压测。

## 6. 备份与容量规划

本次在工程 backups 目录未找到备份文件，也没有做恢复演练。未访问 Supabase 控制台，不能断言用户完全没有其他备份。免费版公开套餐不含自动备份和时间点恢复，需自行确认可恢复的导出方案。[Supabase 官方套餐说明](https://supabase.com/pricing)、[备份文档](https://supabase.com/docs/guides/platform/backups)

按当前学校、研究、目录、指南、事实及索引的平均密度作静态线性估算：

| 规模 | 估计数据库体量 |
| --- | ---: |
| 当前 94 校 | 实测约 39.6 MB |
| 1,000 校 | 约 290 MB |
| 2,000 校 | 约 567 MB |

假设固定开销约 13.6 MB，学校相关表每校均摊约 0.277 MB。当前学校资料密度差异很大；估算不包含新增 PDF/图片、历史版本、用户数据、向量索引和长期日志，不是容量或性能承诺。文件资料应按用途放对象存储，不能为了省事把图片/PDF 二进制都塞进学校 JSON。

当前不必仅为学校数量购买升级；是否升级还应看备份、可用性、真实流量及控制台用量，而不只是容量百分比。

## 7. 建议处理顺序（尚未执行）

1. **权限和恢复保障**：确认备份及恢复方法，收紧匿名/登录角色权限，覆盖全部业务表，验证 BFF 的合法访问仍工作。正式上线前轮换曾在聊天中出现的数据库连接密码，新密码不要再发到聊天里。
2. **统一事实和来源链路**：补来源注册、修复断链；政策文字备注核实后转成带年份、申请对象、来源和审核状态的结构化事实。未知值保持为空，不标成已验证。
3. **解除扩校固定数量限制**：引入动态数量核对、数据批次、幂等导入及失败回滚；不使用“必须 94 校/904 条”的条件验收未来数据。
4. **专业数据标准化**：保留学校原名称，增加标准专业 ID、主辅修/学位/方向类型及学校—专业关系；专业强弱证据单独存储，不能由开设或校排名自动推断。
5. **分批扩充和观测**：先小批增量验证，再扩至 200/500/1,000 校；监测来源完整率、审核覆盖、长尾延迟、失败率和容量。只读报告不是授权执行以上修复。
