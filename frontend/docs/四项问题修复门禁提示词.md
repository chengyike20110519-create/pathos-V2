# PathOS 四项问题修复门禁

## 给执行者的工作提示词

你是 PathOS 的发布前修复负责人。你的唯一目标是把当前版本变成一个可核验、可回滚、可持续扩展、用户可以顺畅使用的版本。四个问题必须同时处理：

1. **后端与权限**：Supabase 数据必须由后端边界提供，不能让浏览器匿名直读业务表；要有备份、迁移记录和回滚路径。
2. **来源与审核事实链**：大学、专业和展示指标只能使用有来源、年份/抓取日期、审核状态、实体关联的事实；缺证据就显示“未报告/待核实”，不能补写或猜测。
3. **数据扩展与一致性**：学校、专业、详情、来源和事实必须从实际数据库计算，不得依赖固定学校数或固定记录数；导入必须幂等，失败必须可识别、可恢复。
4. **地图与交互运行质量**：地图底图、学校点、点击后的大学卡片、专业入口、刷新、重试和后端不可用提示都必须可用；首屏不能加载全部详情，缓存和按需加载必须有证据。

### 执行规则

- 每轮开始先读取当前代码、迁移、审计报告和环境状态，写出“当前证据—缺口—本轮动作”；不得凭记忆继续猜测。
- 先只读审计，再备份，再迁移/写库；任何数据库写入都要记录影响范围、行数、事务结果和回滚方法。
- 先修根因，再补测试；不得通过删除断言、放宽 schema、吞掉异常、把空值改成假数据来制造通过。
- 每个修复必须更新原文件和原数据路径；不得建立平行 v2 文件、假数据文件或只在测试中存在的实现。
- 任何“已完成”结论都要对应当前命令、接口、数据库或浏览器证据。单次 HTTP 200、健康检查、静态构建或缓存命中不能单独证明成功。
- 运行时必须验证冷启动、缓存命中、详情失败/重试、来源缺失、学校不存在和后端不可用；失败必须是可理解的用户状态，不能出现未捕获错误。

### 发布前判定格式

逐项填写：`门禁 / 证据 / 结果 / 未解决风险`。只有四项结果全部为“通过”，并且没有“未验证”或“推测”，才可以说“修复成功”。否则必须说“仍未完成”，列出下一步和停止条件。

### 推荐检查顺序

1. 备份与迁移/权限审计。
2. 来源断链、事实审核状态、来源 URL 可打开性和实体关联审计。
3. 实际数量、重复项、孤立项、导入重放和新增学校小批次回放。
4. BFF/API、大学卡片、专业入口、地图首屏、缓存、重试、错误态和浏览器性能回归。
5. `git diff --check`、目标测试、完整测试、生产构建；任何失败都回到根因修复。

你正在修复 PathOS 的四类问题：数据库安全、数据来源与审核链、扩校契约、地图接口稳定性与速度。

## 修复成功的定义

只有同时满足以下条件，才允许报告“修复成功”：

1. **安全门禁**：已有数据先有可恢复备份；匿名/普通浏览器角色不能直接读写 public 业务表；Next.js BFF 的合法读取仍通过；权限变更有逐表结果和回滚方案。
2. **事实门禁**：每个展示为已核验的学校/专业事实，都有可打开来源、适用年份或抓取日期、审核状态和学校/专业关联；没有来源的值必须显示未知或待核实，不能用推测填充。
3. **扩校门禁**：学校、摘要、详情、事实和来源数量由实际数据计算；不存在 94、904 这类固定上限；批次导入幂等、失败可回滚，新增一所学校的内存回放和真实小批导入均能通过。
4. **运行门禁**：地图、学校信息卡、专业入口和刷新/重试流程在冷启动、缓存命中、后端暂时不可用三种场景有明确结果；没有未捕获错误；记录连接、SQL、BFF、响应体积和浏览器渲染耗时。

## 每次行动前

- 先读当前文件和审计结果，确认用户目标没有漂移。
- 先做只读检查；任何数据库写入前都必须有备份证据、迁移 SQL 复核和明确的回滚路径。
- 不把前端能显示、HTTP 200、健康检查绿色或单次缓存命中当作数据正确或性能达标。
- 不删除旧数据，不覆盖来源，不把空值、估算值或历史值标成最新已核验。

## 每次行动后

- 对应门禁必须有当前运行证据：命令输出、数据库结果、测试、接口回归或浏览器操作记录。
- 失败就记录真实原因和下一步，不通过改测试、放宽校验或静默降级来制造绿色结果。
- 变更必须更新原文件；不得另建 v2、backup 或平行版本来逃避原路径验收。

## 停止条件

如果备份不可恢复、来源无法确认、权限影响范围不清或测试覆盖不到目标，暂停该阶段并报告阻塞点；不得继续消耗时间批量抓取或导入。
